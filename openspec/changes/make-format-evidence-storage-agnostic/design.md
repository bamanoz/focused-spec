# Design

## Context

See proposal.md for motivation and complete scope. Core currently requires `loadEvidenceRegistry` in `sources.ts`, validates focused IDs with `STABLE_ID`, resolves registry rows against parsed items, and emits `Scenario.evidence` to the existing validator/planner. Format API 1 cannot carry evidence and rejects unknown result fields. The historical v0.5.0 parser recognizes `#### Scenario:`, exactly one inline ID and one or more separately backticked EVIDENCE rows; its generic core also used to enforce WHEN/THEN and REVISES. We restore the authoring dialect, not those former core responsibilities.

Fresh proposal authority was obtained from the installed focused-spec 0.9.1, protocol 1/workflow (complete response artifact://2248). This is planning only: no registry, config, plugin, test, guidance or master-spec edits are authorized by creating these artifacts.

## Goals / Non-Goals

**Goals:**
- Both inline and external evidence enter core as the same normalized enrollment, with no YAML evidence loader, source-location policy, metadata dialect or native-ID lookup in core.
- An external adapter can see the complete selected native catalog, report dangling/ambiguous rows and preserve source provenance; an inline adapter requires no external evidence file.
- Preserve every currently protected outcome, exact opaque selector, AND member, scope and shard location through the explicit cutover. IDs are opaque and never renamed or case-normalized.

**Non-Goals:**
- REVISES, owner/revision ancestry, evidence inheritance, autogenerated YAML, format inference, compatibility aliases, background migration, runners API changes, scheduler changes, retries, publication or package-version bumps.
- Core is not forbidden from reading its YAML CLI configuration. The boundary concerns evidence storage, not the configuration serialization format or generic document discovery.

## Decisions

### 1. Format API 2 is a bounded two-phase session

Keep per-document parsing to avoid collecting/re-serializing all source strings in one giant request and to preserve document timing attribution. Add optional catalog-level `bind`, invoked once after all selected native documents are parsed. Both phases run in the same command-scoped isolated format host. Format API 1 is rejected with migration guidance; no v1 wrapper remains in core.

Public shapes (readonly throughout; IPC uses JSON values and removes the local AbortSignal):

```ts
interface SourceLocation { path: string; line: number }
interface ParsedItem {
  line: number
  name: string
  nativeIds: readonly string[]
  markerId?: string
  evidence?: readonly string[]
  evidenceLocations?: readonly SourceLocation[]
}
interface ParseRequest {
  projectRoot: string
  path: string
  source: string
  options: JsonValue
  signal: AbortSignal
}
interface ParseResult { items: readonly ParsedItem[]; diagnostics: readonly FormatDiagnostic[] }
interface CatalogDocument {
  path: string
  scope: string
  items: readonly ParsedItem[]
}
interface BindRequest {
  projectRoot: string
  documents: readonly CatalogDocument[]
  selection: { scope?: string; scenarioId?: string }
  options: JsonValue
  signal: AbortSignal
}
interface Enrollment {
  document: number
  item: number
  id: string
  evidence: readonly string[]
  location: SourceLocation
  evidenceLocations?: readonly SourceLocation[]
}
interface SourceClaim { key: string; location: SourceLocation }
interface BindDiagnostic {
  location: SourceLocation
  message: string
  scope?: string
  focusedId?: string
}
interface BindResult {
  enrollments: readonly Enrollment[]
  diagnostics: readonly BindDiagnostic[]
  sourceClaims: readonly SourceClaim[]
}
interface FormatPlugin {
  apiVersion: 2
  parse(request: ParseRequest): ParseResult | Promise<ParseResult>
  bind?(request: BindRequest): BindResult | Promise<BindResult>
}
```

`FormatDiagnostic` keeps positive optional line, message and optional focusedId for document-local parsing diagnostics. Parsing cannot return a document scope/path override. Core gives each catalog entry its real discovered scope/path and keeps item identity by array index, not source line. `evidence` on a parsed item is a direct enrollment and requires markerId; evidenceLocations requires evidence and, when supplied, has exactly one positive SourceLocation per reference in the same order. Inline supplies each actual EVIDENCE-row location; external bind may supply reference locations and otherwise falls back to its enrollment location. Core reports the offending reference’s location, including a malformed second AND member, without opening origin paths. An absent evidence field is not an empty list and allows external binding. An empty list is an enrollment error, not an opt-out. Bind targets must name actual input document/item indices. An external enrollment of an already marked item must use that marker's exact ID; external native-ID enrollment requires an unmarked item. Core rejects unknown fields, forged targets, malformed responses, conflicting IDs, source claims repeated across adapters, duplicate `(scope, ID)`, and multiple enrollments of one actual item, even when references agree.

`bind` receives the complete catalog, not just the documents parsed by that adapter. This lets one registry adapter preserve the existing logical registry across Markdown, Gherkin and project-native formats and report dangling rows even when its own layout matched no documents. Each configured format referenced by a document layout has a command-scoped session; optional bind is discovered from its validated export and invoked once, including for an empty parse set. Formats without bind contribute only direct parse enrollments. No returned origin path is opened by core. Source claims are opaque keys; core compares them without interpreting file extensions or filesystem layout. The registry adapter supplies canonical project-contained source identities, so overlapping sources cannot be hidden by splitting them between two format registrations.

Adapter diagnostics without selection identity are structural/source failures and always block. Semantic diagnostics carry the known scope/ID and honor selection. Source parse failures, unreadable metadata and YAML syntax/duplicate-field failures never become an empty successful result. Core filters semantic enrollments/diagnostics before selected identity/reference checks; malformed IPC shapes remain format errors. An adapter must not discard a marker without evidence or a row without a unique target: it returns the corresponding diagnostic. Unknown/unselected semantic rows do not poison a selected valid occurrence, but full validation reports them.

### 2. Two official authoring paths, no second evidence plugin system

`@focused-spec/format-inline` parses Markdown structurally. A top-level level-four `Scenario:` heading owns the following scenario body until another scenario/requirement or enclosing section ends. Each declared scenario requires exactly one `- **ID**: \`value\``, at least one separately backticked EVIDENCE row, and exactly one WHEN and THEN row. Metadata belongs to that scenario only. Fenced/indented code and quoted examples do not declare scenarios. Malformed or duplicate metadata fails instead of disappearing. REVISES produces an explicit unsupported-metadata diagnostic; it is not silently consumed. A valid item returns markerId and evidence directly. Plain unrelated native prose is not enrolled. The plugin enforces its own scenario grammar; core does not know heading depth, row labels or WHEN/THEN.

`@focused-spec/format-registry` is a compositional format adapter, not a core-selected backend. Its options name an explicit native parser (`package` or contained `module`, opaque options) and an optional nonempty files list; omission selects the adapter-owned documented `.focused-spec/evidence.yaml` default. Its parse delegates native parsing inside its existing bounded host; its bind reads the existing scopes/evidence/source YAML dialect once per command, resolves marker/native-ID rows against the full supplied catalog and returns normalized enrollments, source claims and diagnostics. Plain Markdown/Gherkin adapters remain structural parsers at API 2; their native parsing does not acquire an implicit registry. Registry binding may enroll their catalog items, but never changes scope or creates a missing item. A direct inline enrollment plus a YAML enrollment is a core conflict, not precedence or merge.

Move existing evidence YAML parsing/discovery/binding into `packages/format-registry/src/registry.ts` and `binding.ts`. Keep explicit-file safety: contained paths, lexical/canonical uniqueness, symlink boundaries, matched dangling links, YAML-only sources, glob bounds, no nested include, no missing-source fallback and closed entry schema. The standalone registry package may own `.focused-spec/evidence.yaml` as an explicitly documented default option; core owns no such default. The proposed configuration examples use explicit files and preserve existing shard ownership.

### 3. Config 5 names formats; it does not configure evidence storage

Inline authoring:

```yaml
version: 5
specifications:
  formats:
    inline: { package: '@focused-spec/format-inline' }
  documents:
    - { match: 'specs/**/*.md', scope: current, format: inline }
runners:
  go: { package: '@focused-spec/runner-go' }
  pytest: { package: '@focused-spec/runner-pytest' }
```

External registry authoring and mixed native parsers:

```yaml
version: 5
specifications:
  formats:
    enrolled-markdown:
      package: '@focused-spec/format-registry'
      options:
        parser: { package: '@focused-spec/format-markdown' }
        files: ['.focused-spec/evidence/**/*.yaml']
    gherkin: { package: '@focused-spec/format-gherkin' }
    inline: { package: '@focused-spec/format-inline' }
  documents:
    - { match: 'openspec/specs/**/spec.md', scope: current, format: enrolled-markdown }
    - { match: 'openspec/changes/{scope}/specs/**/spec.md', format: enrolled-markdown, exclude: ['openspec/changes/archive/**'] }
    - { match: 'features/**/*.feature', scope: current, format: gherkin }
    - { match: 'inline-specs/**/*.md', scope: inline-example, format: inline }
runners:
  vitest: { package: '@focused-spec/runner-vitest' }
```

Core validates only generic registration/layout/options constraints. It rejects top-level evidence, config versions 1–4, unsupported format exports and non-JSON options. Adapter-specific missing files/parser/options errors originate in the adapter. Runner settings, contained document discovery and scope syntax stay unchanged. Native parser delegation is explicit and root-resolved; no extension heuristics, download/global resolution or unbounded nested adapter chains.

### 4. Focused IDs are opaque, stable strings

Core accepts a string with at least one non-whitespace character and no Unicode control characters. It imposes no lowercase, dot, token prefix, case-folding, Unicode normalization or path interpretation. Preserve every character byte-for-byte through binding, CLI selection, JSON output and cross-scope reuse; `Case`, `case`, `auth-login`, `123`, Unicode, spaces and path-looking strings remain distinct values. Formats define representation/escaping. Existing unquoted Markdown markers and Gherkin tags retain native token syntax without a lowercase/dotted check; inline backticks and YAML string keys can represent broader values. A value not expressible by one native token syntax is not silently rewritten to fit it. Current authored repository IDs need not be renamed; dotted names remain a useful convention, not validity policy. Remove repeated focused-ID regex enforcement from core, both official native formats, portable guidance and eval gates. Do not relax document path, source path, scope, format-ID or runner-ID safety as a side effect.

### 5. Keep executable behavior and timings downstream

Normalize direct/external enrollments into existing Scenario/SpecDocument contracts and run the same reference validator, resolution planner and executor. Multiple references remain AND, malformed references cannot hide, planned rows are accepted only non-strict, targets resolve/run once, runner errors and FAIL/SKIP remain authoritative, and no adapter may execute evidence. Syntax-only invokes formats/binding but never runners.

Keep existing timing JSON/text fields and per-document parse rows. Format bind work contributes to validationMs and totalMs, not a fabricated document parse or runner row. A successful parse followed by failed binding retains its completed parse timing and fails validation; no run begins. Do not invent new flags or present internal YAML/parse CPU/subprocess timing.

### 6. Clean cutover and complete owner migration

After separate apply approval:
1. Obtain fresh installed guidance; inspect references with LSP if available (grep only when no TypeScript server is available). Inventory every enrolled occurrence and exact reference before migration.
2. Implement API 2, official formats and the two new packages. Remove core registry loading, binding, STABLE_ID policy and registry exports; move reusable YAML APIs to the registry package rather than leave aliases.
3. Change root config to 5 with one registry-composing Markdown registration; relocate only evidence.files into its options, preserving every shard and native ID. Migrate every root example, fixture generator and custom format module. Do not delete user-owned external files or bulk-convert native items to inline.
4. Update package manifests/lockfile/build order/staging; core before native parsers, inline and registry adapters, then existing runners. Independently pack all eight packages. Core has no dependency on either new adapter or a native parser; its YAML config dependency is unrelated.
5. Update CLI/help, docs and portable guidance with both authoring choices, opaque ID rules, version/API cutover and phase-correct inline evidence writes. An explicit legacy upgrade may retain inline ID/EVIDENCE by selecting the inline adapter and removing REVISES after inventory; it must preserve all identities/references/AND members. It must not force every legacy project to YAML or silently re-enable old config/API readers.
6. Reconcile exact evidence in existing domain shards only during apply. Preserve current bindings for unchanged native items; changed IDs below keep the same identity, repair stale assertions or explicitly replace refs rather than retain false-green coverage. Execute all working evidence with product-regression sensitivity, sync/archive through OpenSpec, publish every surviving occurrence explicitly and retire the working scope.

### 7. Exact executable evidence plan

The final apply registry is derived from the actual delta markers, not a guessed scenario count. `tasks.md` contains the final authoritative `(scope, ID) -> [exact reference]` map for this working scope and later current publication. Existing references are inherited by neither scope: copy them explicitly only after reading their assertions and preserving their AND obligations. No working registry entries are written during proposal.

Reuse existing behavioral tests and update their config/format fixtures. Remove the row in `test/plugins.spec.ts > rejects malformed format responses` that treats `INVALID` as an invalid focused ID: case is now valid; use genuinely malformed shapes/blank/control IDs and preserve the no-execution assertion. Keep plain Markdown rejecting inline rows when the inline adapter was not selected; update its obsolete-format advice rather than globally enable the grammar. Keep YAML closed-schema and source-safety tests under the registry package, including same-line distinct-item binding and double-binding protections.

New exact tests belong to existing suites/files:
- `test/cli.spec.ts`, `focused-spec CLI`: `runs inline ID and EVIDENCE without any registry file`; `preserves opaque IDs through selection and results`; `isolates selected inline errors without inheriting evidence`; `rejects competing inline and external enrollments`; `validates inline planned evidence without loading runners`; `rejects old config and format APIs without fallback`; `runs registry-backed native formats without core evidence configuration`; `reports inline binding failures at their metadata lines`.
- `test/core.spec.ts`, new `inline specification parsing` suite: `rejects missing duplicate and malformed inline metadata`; `ignores literal inline scenario examples`; `rejects REVISES without inventing ancestry`.
- `test/plugins.spec.ts`, `plugin architecture`: `accepts normalized evidence from a storage-independent format`; `rejects forged and multiply bound catalog targets`; `reports adapter binding errors instead of dropping registrations`; `terminates a blocking format binder`; `rejects overlapping opaque evidence source claims`.
- `test/package.spec.ts`, `package distribution`: `executes independently packed inline and registry formats`; `typechecks consumer formats against the storage-independent format API`.
- `test/evals.spec.ts`, existing `agent eval harness`: `preserves inline evidence through revision and publication`; `rejects planning-time inline evidence integration`.

New test cases defend behavior/invariants, not source text, field forwarding, incidental defaults or specific wording. Existing pure help-text/source-layout assertions that merely pin implementation are replaced with real CLI use or removed; do not re-pin them to new text.

Run npm test, npm run smoke, isolated real CLI inline and registry consumers (Go and pytest AND evidence), independently packed consumers and every exact focused reference. For each changed outcome/ref/assertion, an owned disposable product mutation must produce selected behavioral AssertionError FAIL between baseline/restored PASS; missing targets/runner errors/skips do not prove sensitivity. Update public and native agent eval provisioning/judges without weakening protected-product integrity; run both real YAML and inline black-box authoring/revision/lifecycle cases and the current model matrix because package-owned workflow owners change. Record individual failures, missing credentials or transport limitations without calling a partial matrix green. Reload guidance at each focused lifecycle step.

## Risks / Trade-offs

- **Breaking API/config:** API 2/config 5 are deliberate because storage/binding moves out of core; there is no hidden compatibility branch. Package publishing/version changes require separate authorization.
- **Global catalog binding:** One registry adapter may bind other native parsers' items. Core checks exact indices, markers, global item uniqueness and scope/ID rather than trusting source coordinates. Distinct items may share a line.
- **External metadata safety:** Trusted adapters are not sandboxes; moving reading out of core must preserve all observed registry safety contracts and produce source diagnostics. Opaque source claims retain cross-adapter overlap detection without teaching core filesystem ownership.
- **Catalog IPC:** Per-document parsing retains source attribution; bind transmits normalized catalog data once per binding-capable adapter. Avoid copying source text, rereading documents or loading YAML per document. Keep bounded host settlement and JSON validation.
- **Opaque IDs:** Syntax restrictions may remain native representation constraints, never a disguised lowercase/dotted core invariant. CLI args, YAML keys and evidence runner selectors must not be conflated with IDs.
- **Guidance/eval cutover:** Existing procedures hard-code registry authoring and numeric ID gates. Update those owners and actual matrix evidence in the same apply; do not claim skill readiness from unit tests alone.
