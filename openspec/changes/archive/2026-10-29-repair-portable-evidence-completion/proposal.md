# Proposal

## Why

The fresh `externcash/gpt-6.1-sol` matrix completed all 40 invocations without provider-402 errors, but 16 invocations failed: seven native enrollment omissions, seven public workflows with chained guidance acquisition, one missing SDK composition-topic acquisition, and one reproduced evaluator PATH mismatch. Improve the portable decision points and repair the evaluator without patching individual host workflows or weakening approval, integrity, or evidence gates.

## What Changes

- Make the loader's initial workflow request explicitly separate from executable/version checks; keep full-response recovery and later topic procedure owned by the package router.
- Give author/revise guidance a short, framework-neutral pre-write decision: requested deliverable, actual host phase/authorization, established composition, native identity/evidence obligations, and exact remaining work. A wording revision is not automatically planning-only, and existing tests do not remove enrollment obligations.
- Include discovered required auxiliary metadata in approval proposals rather than recommending an unenrolled wording-only substitute. A real user exclusion remains authoritative; report its consequences without silently dropping the original obligation or writing outside approval.
- Clarify when installing a missing scenario execution dependency establishes the first composition, including SDK-only work, rather than repairing an already established compatible dependency.
- Resolve bare CLI commands with the same effective PATH as the evaluated agent, while preserving explicit external installations and fail-closed provenance, response, artifact, and standalone-command checks.
- Report a missing binding as a missing binding: do not claim native behavior was lost when its bound outcome could not be judged. Keep the failing enrollment verdict and dependent unverified checks.
- Preserve the intended outcome in the tool-free planning test user's replies without suggesting undisclosed implementation mechanics or synthesizing approval.
- Rerun the complete freshly discovered public/native matrix after implementation, retain every result, and distinguish failed, passed, and unverified aspects. Historical scores remain immutable.
- Separate integration-topic acquisition observations from task-success gates. Per the user's correction, a correct composition and independently verified outcome must not fail solely because the agent did not read `integration`; preserve the observation, behavioral checks and immutable historical scores.

## Capabilities

### New Capabilities

None. Reuse the existing workflow/evaluation boundary.

### Modified Capabilities

- `agent-workflow`: clarify authorization-aware enrollment and first-composition decisions, establish driver-equivalent acquisition resolution, and make prerequisite-dependent native diagnostics explicit.

## Impact

Planned product-facing owners: `skills/focused-spec/SKILL.md`, `guidance/workflow.md`, `guidance/author-revise.md`, and, where completion wording needs the same distinction, `guidance/verify.md`. Evaluator owners: `evals/omp-agent.ts`, `evals/acp-agent.ts`, `evals/judge.ts`, and `evals/native-pilot.ts`; neighboring behavioral checks belong in `test/evals.spec.ts`, `test/native-pilot.spec.ts`, and the existing consent suites only where a real changed boundary needs them.

Implementation will bind the delta and current occurrences separately in `.focused-spec/evidence/agent-workflow.yaml`, update `docs/development/agent-evals.md` and `docs/development/candidate-improvements.md`, and check root README accuracy. No package/API version change, release, host-specific portable procedure, rewritten official host skill, new completion command, or fixture prompt disclosure is proposed. Other recorded improvement blocks remain separate work; this proposal does not cancel them.

This change is planning-only until a subsequent apply request. No executable integration, tests, package guidance, or evaluator source is changed by this proposal. Exact baseline artifacts, replay evidence, proposed selectors, and verification are recorded in design/tasks.
