# Design

## Context

See [proposal.md](./proposal.md). The repository currently has a long root README with overlapping setup sections, a detailed ownership-oriented docs map, relative links copied into the core package, and one general runner guide staged as every runner package README. Current install guidance already notes that Python/.NET CLI plugins are prepared in checkout but publication is separate; package READMEs and some runner docs still offer npm install commands for them. The worktree example uses checkout-relative dependencies, and the installed root README currently points agent installation at `main`.

## Goals / Non-Goals

**Goals:** Make the documentation path coherent from repository README through the installed core package and individual plugin pages; keep claims grounded in available artifacts and the actual consumer context.

**Non-Goals:** Change SDK or CLI behavior, publish packages, alter guidance acquisition/skill activation, edit .NET installation sections owned by the distribution change, or add integrations with OpenSpec or Spec Kit.

## Decisions

1. Treat documentation as user-visible behavior. Keep one concise root path chooser for SDK-only scenarios and CLI-based evidence; put procedural detail in existing guides. The inline example must install exactly the referenced format and runner and point at a real Vitest test.
2. Describe focused-spec as a generic evidence layer that preserves the host specification and lifecycle. Mention frameworks only as examples of compatible native sources, not as product-owned integrations.
3. Pin the agent-install URL to the current release tag. Describe npm availability based on actual publication state: provide checkout-based installation instructions only where those packages are prepared locally, and do not suggest that registry install succeeds for unpublished packages.
4. Correct source-relative README links during staging, preserving usable public destinations in the staged core README. Use the verified raw `main` banner because the release-tagged asset does not exist; disclose the unpublished onboarding fixture as a checkout-only code path while preserving the complete runnable inline example. Package, example, docs and license links retain their existing tagged destinations, and agent installation remains release-pinned. Replace the shared runner-guide copy with package-specific runner READMEs; the runner guide remains the canonical comprehensive guide.
5. Make worktree instructions reproducible from the checkout-relative dependency layout, or label that example explicitly as checkout-bound. Shorten `docs/README.md` to navigational entries and remove links to the internal candidate register. Remove references to ignored eval output from tracked user documentation rather than trying to publish local paths.
6. Keep the distribution proposal as owner of .NET SDK NuGet/installation material. Where a documentation item touches a shared page, this change may clarify non-.NET portions but must leave that owned section untouched; coordinate plugin availability wording with that proposal.
7. Keep editorial judgment separate from executable evidence. The approved apply assignment adds local link/anchor/index-reachability checks and enrolls the actual inline consumer and navigation selectors; it does not turn copy review into source-text assertions or claim that unrelated passing tests prove static wording.

## Risks / Trade-offs

- Registry publication can change independently of source. Wording should state the observed current availability and avoid implying a guarantee for later releases; future releases should update the corresponding package README as part of publication.
- Rewriting staged Markdown links can accidentally affect links meant to remain relative within a package. Validate the staged README in the packed core context and keep changes limited to known repository-relative destinations.
- Shortening navigation can hide maintainer resources if over-applied. Preserve an explicit development section while removing internal candidate tracking from user navigation.
- Package-specific runner READMEs may repeat a small amount of canonical guide content; link back to the guide for shared policy and keep each package page limited to its own contract.
