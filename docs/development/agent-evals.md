# Agent evaluations

The eval harness provisions a clean workspace, installs the packed CLI, copies only selected skills, runs an OMP agent, and judges the resulting behavior. `npm run eval:agent` builds the product once before starting the harness; direct strip-types invocation requires an existing build. Provisioning packs with lifecycle scripts disabled into each workspace's independently owned temporary package directory, so it does not rebuild shared `dist` or replace another workspace's tarball. Cleanup removes both the evaluated workspace and its package artifacts.

Each public workflow turn starts a fresh session in an independently owned directory beside its workspace, with no resume. Persisted output artifacts let the agent recover complete protocol JSON when the host clips long lines; `--no-session` would discard that recovery path. Workspace cleanup also removes those session directories.

## Cases

```sh
npm run eval:agent -- --list
```

- `files-source-bootstrap`: bind a native file-backed item and create Go/pytest runners.
- `vacuous-evidence`: change Python authentication to reject blocked accounts while keeping its pre-existing evidence selector. The initial product permits blocked accounts, and its falsely green test only checks that the returned value is a boolean. The prompt does not reveal the test defect or prescribe a mutation probe. The agent may change only the relevant Python implementation and test; Go, unrelated Python tests, the preconfigured runner, installed skills, and package files stay protected. Gates independently check all four authentication outcomes, require the repaired selected test and focused evidence to fail when blocked-account protection is removed, verify restoration, and require the agent's own transcript to contain focused PASS → selected assertion FAIL → restored PASS.
- `openspec-apply`: apply an existing OpenSpec change.
- `openspec-propose-apply`: proposal turn followed by a fresh apply turn.
- `full-skill-routing`: with all OpenSpec skills available and no mention of focused-spec in the prompts or change name, choose both the host workflow and the focused-spec skill, plan at least one exact test for the existing behavior, and execute its focused evidence. Either the Go unit test or the pytest functional test is valid; if both are chosen, both must pass.
- `openspec-brownfield`: adopt focused-spec in an OpenSpec project whose main specification was produced by a real, isolated OpenSpec 1.6.0 proposal/apply/sync/archive of blocked-account behavior without the focused-spec CLI or skill. The case overlay contains the resulting `account-authentication` spec, archived change, and Go/Python implementation and tests. An apply turn binds the existing blocked-valid-credentials Scenario and independently validates and executes both working evidence targets at a harness checkpoint. A fresh sync turn publishes the native binding and evidence while leaving the other three native scenarios unmarked. Final validation, execution, and controlled mutations use the surviving main scope from project configuration, even when working discovery has ended. Lifecycle gates compare the checkpoint's executed references with explicit main and retained working evidence and execute main evidence again with the working document absent. A delta-only pass, missing checkpoint, or changed evidence cannot pass; no cross-scope ownership link is required.
- `registry-shards-reuse`: a blind native authentication revision in a project whose authentication and notification domains already own separate configured registries. The agent must use both existing authentication tests, append to the existing authentication shard, and preserve its prior registration and the unrelated domain. The prompt names neither focused-spec nor registry sources.
- `registry-shards-new-boundary`: the same blind authentication revision in a project with only notification evidence enrolled. The new authentication domain must own one newly connected registry source; the existing notification source, native item, implementation, tests and runners remain protected. The agent chooses the new shard name and focused identity.
- `project-upgrade`: only `Обнови focused-spec до последней версии.` starts with genuine published 0.5.0, its full-text skill, runnable version-2 configuration and three enrolled occurrences, including a repeated ID in an independent captured scope. Provisioning first validates/runs that actual legacy CLI. A disposable loopback npm registry makes the independently packed unpublished candidate available as latest through ordinary npm installation; unrelated packages redirect to public npm. The registry closes after evaluation even with a retained workspace. Independent candidate file hashes replace—not discard—package/selected-integration protection for this case only. Final gates reject extra/stale/modified package or integration files, lost or redirected scope-local IDs/evidence, omitted AND selectors, changed native behavior, runner/execution configuration or unrelated manifest dependencies. Product/tests/runners remain protected. Controlled Go and pytest regressions require the migrated selected assertion to fail and pass again after restoration.

The working checkpoint retains the independently executed references and native outcome before publication, so physical removal or archive of the working document does not discard the proof. Final gates never re-enable expired discovery or inherit its evidence: main must explicitly declare the same references and execute them itself. OpenSpec completion checks resolve the actual active or archived change tasks. Completion-judge exceptions are recorded as a failed `evaluation-error` gate rather than discarding the run's captured turns.

A working checkpoint also survives retirement of its marker and registry entry when the now-unmarked native delta remains discoverable. Only an independently passing pre-transition checkpoint may supply that historical working proof; main evidence must still be explicitly bound and executed. An active working binding continues to be checked against its live registry rather than hidden by the checkpoint.

The brownfield baseline was captured from a disposable Go/Python project where authentication initially checked credentials but not blocked status. An agent with only OpenSpec skills implemented the change, verified Go/Python behavior, and archived it; its unmodified final spec has four native `WHEN`/`THEN` scenarios and no focused binding. The later evidence-binding delta is the eval task, not part of that bare OpenSpec run. Its archived baseline is protected against modifications by the eval agent.

OpenSpec cases require a skills source:

```sh
npm run eval:agent -- \
  --case openspec-propose-apply \
  --openspec-skills /path/to/openspec-skills \
  --timeout 1200
```

## Judged invariants
- strict focused-spec validation and real evidence execution pass;
- each public workflow turn and each distinct native authoring/regeneration workflow completes a focused-spec loader read and obtains valid protocol-1 workflow guidance from its project-local installed CLI; conversational clarification or approval replies alone are not new workflow boundaries. Host-truncated CLI output counts only after a subsequent completed read of that successful command's linked artifact delivers the full valid response. Command starts, failed responses, unrelated/global installations, help, or runner guidance alone do not activate the workflow;
- OpenSpec validation and tasks are complete when applicable;
- selected Go and/or pytest evidence actually executes and passes; cases that explicitly require both languages check both;
- existing product tests remain unchanged and pass, except the explicitly editable Python test and implementation in `vacuous-evidence`; its unrelated tests and runner remain protected;
- controlled regressions in every selected implementation make its focused evidence fail;
- judged identity is the `(scope, ID)` pair: selected-scope checks ignore same-ID entries elsewhere, while all-scope checks judge every entry against its own explicit binding and evidence;
- an exact focused ID is required only when the task or pre-existing source supplies it; otherwise one valid authored binding is selected, frozen at the first successful checkpoint, and retained through apply/publication; missing, ambiguous, invalid, or renamed identities fail independently of passing evidence;
- a named change is not an undisclosed scope label: completion selects the one configured scope containing that change's native documents, rejects missing/ambiguous selections, and uses it for CLI, identity and controlled-mutation checks; equivalent exact Go file/package selectors are accepted;
- lifecycle checks independently execute working evidence before publication, stop before the next turn when it fails, and require the same explicit binding and evidence to survive and execute in the configured main scope after working discovery ends; they do not rely on an owner, revision edge, inherited evidence, or an agent's claimed PASS;
- native agent-execution judgment requires a completed successful test command or installed CLI run reporting the exact selected evidence; validation, help, incomplete calls, failed commands and unrelated references do not count;
- the agent does not inspect implementation source or use `shell: true`; public package README/reference documentation and type declarations are permitted, but package `src/`, compiled `dist/` JavaScript, and executable example source are implementation inspection. Invoking the explicit installed `dist/cli.js` with Node is CLI execution, not source inspection. Reading/searching that file or reading it through a shell/inline script still fails integrity, including when combined with a legitimate CLI invocation;
- proposal turns do not start implementation.
- registry placement cases independently load the configured sources, preserve every original registration at its original domain location, reject an added default monolith, and require either existing-domain reuse or exactly one explicitly connected new-domain source; configuration outside `evidence.files` remains unchanged. Unconfigured new evidence and domain-wide reorganization cannot satisfy this gate.
- upgrade cases retain an independently owned pre-migration inventory and candidate artifact expectation; a green remaining selection cannot hide lost legacy outcomes or package tampering. Non-upgrade cases retain unchanged installed-package/skill protection.

The result is written to gitignored `evals/results/<case>-<timestamp>.json`. `--keep-workspace` retains the isolated workspace for diagnosis. A model-specific pass is evidence for that model and prompt; it is not a universal capability claim.

Saved results are immutable. If a gate bug is corrected, captured transcripts may be replayed to verify that correction, but the original model score remains unchanged and the replay is not a new model evaluation.

For instruction-distribution changes, completion requires fresh runs of every listed public case and every native host in both revision and `--create` modes: currently nine public and 14 native runs. Re-discover cases before running and include new cases rather than freezing this count. Record each model, invocation, immutable result artifact, gate verdict, and exit status; a subset or skipped case is not a complete run. Guidance acquisition is not executable evidence. Old full-text-skill result files retain their historical contract and are not rewritten or relabelled as new-loader runs.

## Native-ID authoring evaluation

The separate black-box authoring evaluation established the production identity and evidence protocol against host-owned checkable items. Editable items carry a marker or Gherkin tag; the BMad case binds its generated kernel's stable `CAP-1` through registry `source.path` and `source.nativeId` without modifying the derived spec. Each agent receives a plain request to create or revise the host specification for blocked-account login, with no focused ID, evidence path, selector, skill-reading instruction, or prohibition on companion files. In revision mode the existing item rejects blocked accounts without saying what happens when their credentials are valid, so the evaluated change must sharpen that same item rather than duplicate it.

```sh
node --experimental-strip-types evals/native-pilot.ts openspec externcash/gpt-6-sol
```

Add `--create` to start without the native document and evaluate whether the agent authors the checkable item, identity, and evidence from scratch. The default mode starts with an incomplete native outcome and checks that the same atomic result is revised rather than duplicated. The creation gate checks each host's native item shape and one focused binding; it does not replace unavailable host validators. The BMad case installs its official project skills and scripts, checks memlog use, then removes the derived kernel and invokes `bmad-spec` in a fresh agent turn to rederive it from `.memlog.md`. Its lifecycle verdict requires the same unique `CAP-1` outcome, unchanged registry binding, single behavior source, and protected product/tests after regeneration. The GSD case installs official project-scoped Pi workflow assets under an isolated HOME; their later lifecycle transitions are not exercised.

BMad regeneration uses its own fresh persisted session, never the prior authoring context, so clipped guidance can be recovered through that call's output artifacts. Creation identity checks use the CLI parser's actual bound item rather than a hidden scenario/acceptance-heading convention: an OpenSpec requirement heading or Agent OS shaping subsection can own the outcome. The bound item itself must contain the blocked/valid/rejected conditions; an unrelated marked section, detached or duplicate marker, and malformed native syntax still fail.
The regeneration memlog gate accepts project-relative or exact in-project absolute paths and read selectors. It requires a paired successful read completion before kernel derivation starts; a failed or unfinished read, a same-named source outside the workspace, or a read after writing the kernel cannot establish canonical derivation.
Negated authentication wording such as “must not log in” or “is not authenticated” expresses rejection; it is not required to use an undisclosed `rejected` token. A statement permitting blocked login still fails the bound-outcome check.

Kiro creation accepts the event-driven [EARS grammar](https://alistairmavin.com/ears/) with a named system (`WHEN <trigger>, THE <system name> SHALL <response>`), not only the example's literal `THE SYSTEM SHALL`. Trigger, obligation, attached unique identity, and blocked/valid/rejection semantics remain required. Installed GSD `.pi/gsd-core/` resources and its isolated `.home/.npm/` dependency cache are not native project behavior sources; project duplicates still fail, and installed GSD resources are protected by infrastructure integrity checks.

Native fixtures register their existing protected Go and pytest runner modules in project configuration before authoring; agents select evidence against those actual project-local selector contracts rather than needing to create replacement runners. BMad outcome gates accept equivalent denial wording while retaining one unmarked native capability, the blocked/valid/rejection conditions, and unique external binding.

Host guidance is provisioned separately from the portable focused-spec skill. OpenSpec receives its propose, update, and explore skills: creation starts without a prebuilt change and is judged against proposal guidance, while revision is judged against the planning-only update workflow. GSD uses one pinned official Pi installation, not a separate unconverted skill from another runtime. Its installed new-project workflow and requirements template are exposed verbatim as local `gsd-new-project` and `gsd-requirements` skills with discovery frontmatter and source provenance. Preparation rejects stale Claude-home guidance and checks concrete referenced Markdown assets exist. A host read counts only after its matching `read` completion succeeds; line ranges and `raw` selectors are accepted, but failed, incomplete, and lookalike-path reads are not.

GSD discovery descriptions distinguish the requirements-format template for an initialized project from the new-project workflow used for initial authoring; the official workflow and template bodies remain unchanged.

Spec Kit exposes its genuinely installed `speckit.specify` command and specification template verbatim through `speckit-specify`, recording the installed integration version and original paths. Its orchestration registry and initialization alone are not authoring guidance. BMad adds a discoverable host integration resource describing generic generated-kernel ownership and stable `CAP-N` external identities; it neither changes nor substitutes for the official `bmad-spec` workflow. Neither resource contains the task's focused ID or evidence selector.

Kiro and Agent OS fixtures download genuine Markdown from the [Kiro requirements-first documentation](https://kiro.dev/docs/specs/feature-specs/requirements-first.md) and the [Agent OS shape-spec command](https://github.com/buildermethods/agent-os/blob/main/commands/agent-os/shape-spec.md), respectively. They expose it verbatim under local `kiro-requirements` and `agent-os-shape-spec` skills, adding only discovery frontmatter and source provenance. Download errors or non-Markdown responses abort fixture preparation. These resources do not supply focused IDs or evidence hints. Their native constraints remain intact: Kiro requirements review precedes design and tasks; Agent OS shaping runs in genuine read-only plan mode with explicit user questions and plan confirmation. Loading guidance alone is not certification of execution or lifecycle.

An editable item with a preserved focused marker/tag does not need an additional native ID. The marker/tag must resolve to one adjacent item; an external binding instead requires a stable native ID resolving uniquely at its source path. The portable skill keeps these branches explicit without host-specific examples.

The companion single-source gate counts parsed native items, not marker-like strings. A saved native plan may quote the proposed artifact in a fenced code block without creating another item; Markdown marker examples, quoted Gherkin tags, and fenced BMad capabilities do not enroll a source. A second live marked item or explicit BMad capability still fails, as do malformed or detached bindings and obsolete scenario companions. This does not change official host workflows or replace native format validation.

OpenSpec creation/revision and Kiro requirements authoring run as bounded conversations, not a single unanswered request. After each authoring turn, a separate tool-free, skill-free test-user agent receives only the original task and the assistant/user conversation. It answers clarifications or confirms concretely proposed in-scope revisions; it receives no scored gates, workspace files, evidence selectors, or diagnostic interview. Its reply resumes the same persisted authoring session. A generic system note tells the authoring agent that user replies are available and that it should stop to await them; the blind task is unchanged. No official workflow is patched or relaxed. Kiro review can complete the requested native item and existing-test integration without authorizing unrelated design, tasks, or product implementation.

The result's `dialogue` records every authoring turn, test-user reply, exact approved file paths, and test-user transcript. A reply must be valid JSON; approved paths must be project-relative and occur as complete paths in the task or proposed revisions, not merely as basenames inside longer paths. The test user copies complete proposed paths without shortening them and asks for clarification when a basename does not identify its destination unambiguously. Eight authoring turns bound the conversation; exhaustion or an invalid responder fails `authoring-dialogue`, not a fabricated completion. For OpenSpec revisions, a filesystem comparison after each turn detects writes before approval or to different files. Approval is consumed by the next revision of that file and is never retroactive. These violations fail `host-write-constraints`; ordinary native-item, registry, execution, sensitivity, and OpenSpec-format checks run on completed conversations.

Agent OS uses real OMP ACP `session/set_mode` with `plan` and advertises form elicitation. A protected runtime extension exposes `AskUserQuestion` through that actual UI transport and states that mandatory host interactions take precedence over generic question-minimization and assumption heuristics; the official workflow remains unchanged. A separate tool-free, skill-free test-user answers only the original task, assistant conversation/proposed plan, and current question/schema, with no workspace files or gates. Question answers cannot authorize filesystem writes: only the runtime's separate explicit plan approval, not `--plan-yolo`, permits the transition to execution. The result's `planning` retains protocol frames, decisions, responder transcripts, and journal-derived tool events. Filesystem comparisons before answers and after completion reject writes before approval or to unapproved paths; approval is consumed by the next observed revision. Private execution journals and local plan artifacts are not native specification sources. Unavailable transports leave prerequisites unverified; entering plan mode without actual questions or plan approval does not certify authoring.

ACP consent validation uses the full locally submitted plan, not only the runtime's clipped approval preview. Proposal input may be `slug` or `slug/title`; the slug selects `local://<slug>-plan.md`. An explicitly named directory followed by exact backticked companion basenames “in that same folder”, or explicit `Write`, `Create`, or `Generate` paragraphs naming those files, identifies those paths in the nearest named directory. A compact backticked list may anchor companion basenames to an explicit full file path only when all full paths in that list share one directory. Neither form authorizes other folders, unnamed files, or ambiguous mixed-directory companions. Decoded responder decisions and transcripts are retained before proposed-path validation, so a rejected approval records the requested paths instead of resembling an unexplained transport cancellation. Explicit approval and per-revision filesystem auditing remain required.

At genuine runtime approval, the harness rereads the current plan file from its completed ACP resource location and supplies that exact full plan to both the test user and path validator. Later edits therefore replace the initial write's contents; missing resources fail rather than falling back to stale text. The runtime's clipped preview remains recorded separately.

Exact file creation proposals establish their parent directory for subsequent relative creation statements, ordered or bullet file lists, and named payload headers. The parser follows visible declarations in source order, so a later task cannot change the directory of an earlier payload. Only explicit creation operands contribute candidate directories; reference paths in explanatory text do not. When more than one creation directory is possible, relative names remain ambiguous unless the plan explicitly establishes their directory. Deferred creation and declarations immediately below Markdown headings follow the same rule. Exact backticked filename payload headers also name proposed files, including `Exact` filename `contents:` declarations. Relative names inside fenced payloads do not grant permission.

An explicitly named subdirectory does not replace its parent document directory when resolving companion basenames. Naming a nested directory does not authorize moving those companion files into it.

Replace `openspec` with each case name. Results are saved to gitignored `evals/results/native-*.json`, including the agent transcript, individual gates, and independent `authoring`, `evidence`, `nativeValidation`, and `nativeLifecycle` verdicts (`passed`, `failed`, or `unverified`). `certified` requires all four to pass: an unavailable checker or unexercised lifecycle is **unverified**, not successful host validation. The process exits 1 for a failed verdict, 2 for unverified-only results, and 0 only when certified. OpenSpec format validation uses `openspec validate link-blocked-account --strict --no-interactive`; Gherkin syntax uses the official `@cucumber/gherkin` parser, not a lifecycle command. Spec Kit has a real `specify init` installation but no spec-format validation command. Kiro's IDE is unavailable; BMad, GSD Core, and Agent OS have no runnable native format validator in these fixtures. Agent OS's runtime planning/confirmation bridge does not supply one. BMad regeneration verifies retention, not format validity. None of these pilot results certifies the current focused-spec CLI.

When the registry is missing or invalid, its gate reports the specific rejection cause (shape, identity, native binding, selected evidence, or duplicated behavior). Dependent agent-execution, test-execution, and sensitivity gates have `passed: null` and `blockedBy: "evidence-only-registry"`, and print `BLOCKED` rather than `FAIL`. They do not assert that no test ran or that a test failed. A verdict with only blocked checks is `unverified`; an actual failed gate still makes its verdict `failed`. Certification requirements and BMad-specific authoring/regeneration rules are unchanged.

## Post-failure research interviews

Public and native evaluations use the same read-only post-eval research interview after all scoring and lifecycle checks. If a judged gate fails, the harness resumes that agent's own persisted session before workspace cleanup: the last attempted public workflow turn, or the last attempted native phase (lifecycle when it ran, otherwise authoring). It shows observed gaps and asks for concrete fixes to instructions, fixture, or gates: the exact place and suggested wording or change, the evidence behind each proposal, and how to check the fix. Portable loader and CLI-owned guidance remain framework-agnostic; host-specific paths and commands belong in host guidance or the installation fixture. Keep the agent-facing eval request blind; do not leak skill names, IDs, selectors, or gate expectations into its prompt or judge artifacts.

The result stores a separate `diagnostic` with `status` (`answered` or `unavailable`), `answer`, `transcript`, and `detail`; successful evaluations have `diagnostic: null`. Research has only the `read` tool and a two-minute limit. Its success, failure, or unavailable session never changes the scored turns, gates, verdict, or process exit code. Missing or ambiguous session journals, interview errors, and an absent completed answer are recorded as unavailable rather than discarding the evaluation. The CLI reports diagnostic availability; the complete recommendations are in the saved result. Historical records are not rewritten, and a new interview is not a retry of the scored task.
