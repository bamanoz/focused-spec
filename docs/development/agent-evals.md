# Agent evaluations

The eval harness provisions a clean workspace, installs independently packed core/adapter packages, copies only selected skills, runs an OMP agent, and judges the resulting behavior. `npm run eval:agent` builds the private workspace once before starting the harness; direct strip-types invocation requires an existing build. Provisioning packs with lifecycle scripts disabled into each workspace's independently owned temporary package directory, so it does not rebuild shared `packages/core/dist` or replace another workspace's tarballs. Cleanup removes both the evaluated workspace and its package artifacts.
Fixture/reference installs prefer cached dependency metadata using npm's `--prefer-offline`, matching ordinary fixture provisioning. Cache misses still use the configured registry; peer resolution, independently packed candidate bytes, install deadlines, and all evaluation gates are unchanged. This avoids needless stale-metadata revalidation making an already cached fixture depend on registry latency.

Each public workflow turn starts a fresh session in an independently owned directory beside its workspace, with no resume. Persisted output artifacts let the agent recover complete protocol JSON when the host clips long lines; `--no-session` would discard that recovery path. Workspace cleanup also removes those session directories.
The ordinary and ACP drivers share one effective environment: the consuming project's `node_modules/.bin` precedes the inherited supervisor `PATH`. Guidance acquisition resolves bare executable commands in that same order, stops at the first selected executable even when it is not focused-spec, and checks the serving installation's package and topic asset. Explicit external executable paths retain their own installation identity. The gate does not change `process.env` or substitute the supervisor's installation.
An exact `npx --no-install focused-spec instructions ...` request may establish acquisition only when the consuming project's `node_modules/.bin/focused-spec` resolves to the serving installed package. It never falls through to a cached, PATH, global, versioned, or downloadable package; plain `npx` and chained commands do not establish this provenance. Complete package/topic response and matching artifact recovery checks still apply.

Native acquisition is session-scoped. The first scored execution in each native authoring or publication context must complete a valid workflow acquisition; a later read cannot repair a missing or invalid initial acquisition. A clarification or approval continuation may reuse that acquisition only when it resumes the same persisted session directory and journal and the selected executable, canonical package installation, package version, and exact workflow content remain unchanged. A fresh session, absent or different resume journal, changed or missing installation, changed canonical selection, version, or content requires a current valid acquisition. Acquisition is captured against the installation present at each execution boundary, so a later package state does not retroactively invalidate an earlier accepted response.

Missing a redundant read on an eligible unchanged native continuation is saved as a false `focused-workflow-reacquired` or `lifecycle-focused-workflow-reacquired` observation. It is not a gate and cannot change authoring or lifecycle verdicts, certification, exit status, or failure-interview selection. Public workflow turns still start fresh contexts, and BMad regeneration remains an independent acquisition context. This is evaluator behavior only: the distributed loader/router, package guidance, prompts, host approvals, and lifecycle procedure are unchanged.

### Integration and executable-authoring ownership

These variants use case-specific provisioning in `evals/integration.ts` through the existing public harness, driver and immutable result store. Only core is initially installed for first integration. Candidate tarballs and expected package-file hashes live outside the evaluated workspace; a disposable loopback scoped npm registry exposes unpublished plugins to normal package-manager commands. It closes after each case. Go SDK fixtures have an explicit local module replacement rather than pretending an unpublished remote version exists.

Judges compare actual dependency, configuration and source effects against the requested phase and composition. Installed guidance recommends a completed same-installation `integration` response before a first dependency choice, but acquisition is recorded in `EvalResult.observations`, not task-success `gates`. When first selection is needed, a missing, invalid or late response remains a false observation with its actual provenance detail; it cannot alone fail a correctly completed task, change the exit status or trigger a failure interview. Initial composition is captured before the agent acts, not inferred from the case's `integrate` label or from the final installation. An existing JS/TS suite recognized by the shared static catalog establishes its SDK choice even when the manifest and installed package are missing; comments or unparseable source do not. The Go SDK fixture already selects its local module and imports it in both the native suite and ordinary tests. Retained composition reports a satisfied routing check with an explicit retained-composition detail, not a missing-read warning or a claim that guidance was read. Missing CLI format/runner choices still require first-composition routing. Correct composition, authorization, preserved native source, package integrity, real execution and application-regression sensitivity remain blocking. Other loader/workflow activation and selected-plugin contract gates remain unchanged. Historical results are immutable; replay is not a fresh model pass.
Selected plugin-document recovery accepts both supported full-output footer shapes, including a subsequent clipped read linking another artifact. Each successful read retains the originating package selection and must deliver the exact installed document before a configuration write; failed, incomplete, unrelated or stale recovery cannot establish acquisition.

Executable gates preserve a single suite, independently check its claimed withdrawal expectation, run ordinary language tests, mutate only the real application boundary, require the selected behavioral assertion to fail and verify restored success. CLI variants additionally execute that same selected occurrence under regression and the completed configured scope. An expectation echo, self-derived oracle, hidden result projection, duplicate Markdown/registry, diagnostic-only success, skip, missing target or setup/runner error cannot substitute for proof. Package/SDK/application integrity remains independent of agent prose. Deterministic judge-boundary tests protect these verdicts; fresh model runs separately assess the guidance's effect.

BDD activation is assessed without an SDD host by fresh `integration-standalone-typescript-sdk`, `integration-standalone-go-sdk`, and `executable-authoring-sdk` runs. The prompts do not prescribe skill loading; each turn must complete a loader read, select one installed CLI with observable provenance, and acquire current workflow guidance from that same executable before downstream judgment, even though execution stays SDK-only. A fixture may provide an explicit executable outside the project; a compatible project/workspace installation remains preferred when present, and PATH/global is otherwise supported. `full-skill-routing` separately protects host workflow selection and proposal/apply boundaries. The SDK-only activation regression in `test/evals.spec.ts` checks that a successful exit without either prerequisite stops before composition/behavior judgments. That deterministic rejection check does not prove autonomous model selection: retain and report each live case/model result, including failures and timeouts, without claiming a broader model or language matrix.

Run each listed variant separately with `--case <id> --model <model>` and retain every invocation/result. Always rediscover `--list` before the complete rerun; these variants join, rather than replace, the existing public and native-host matrix.

The working checkpoint retains the independently executed references and native outcome before publication, so physical removal or archive of the working document does not discard the proof. Final gates never re-enable expired discovery or inherit its evidence: main must explicitly declare the same references and execute them itself. OpenSpec completion checks resolve the actual active or archived change tasks. Completion-judge exceptions are recorded as a failed `evaluation-error` gate rather than discarding the run's captured turns.

Inline publication keeps unrelated history in valid, unenrolled native specifications outside the selected inline layout. Final scenario and controlled-regression gates judge the configured main scope, including an explicit scope passed by completion; working checkpoints still require the named change's native item.

A working checkpoint also survives retirement of its marker and registry entry when the now-unmarked native delta remains discoverable. Only an independently passing pre-transition checkpoint may supply that historical working proof; main evidence must still be explicitly bound and executed. An active working binding continues to be checked against its live registry rather than hidden by the checkpoint.

### Competing-skill activation experiment

Run the matched baseline and competing-catalog case with the same model:

```sh
npm run eval:agent -- --case full-skill-routing --model <model> --openspec-skills /path/to/openspec-skills
npm run eval:agent -- --case blind-skill-activation --model <model> --openspec-skills /path/to/openspec-skills --competing-skills /path/to/installed-skills
```

`--competing-skills` (or `COMPETING_SKILLS_DIR`) supplies a directory of installed `<name>/SKILL.md` trees, not synthetic descriptions or private host context files. The case copies all additional trees, including reference/script assets, into the isolated workspace; each must declare its matching name and a nonempty description. The independently packed focused-spec loader and explicitly selected OpenSpec skills take precedence over same-name entries. A missing source or catalog with no additional skills fails provisioning rather than silently running the baseline. Other cases retain their original selected skills.

The immutable result records the complete competing-case skill inventory and SHA-256 of every copied skill file. Those files are protected from evaluated-agent modification. `focused-skill-loaded` and same-installation `focused-workflow-acquired` are checked for each executed turn before phase/behavior judgment; activation failure remains a failed result, not a behavioral retry. Reuse the existing exact-evidence, planning-boundary and application-regression gates; merely reading a skill is not task success.

All newly saved public-harness results include `measurements`: summed agent-turn `durationMs`, summed completed assistant-message token usage (`input`, `output`, `cacheRead`, `cacheWrite`, `totalTokens`), and `usageComplete`. Repeated turn/end-session message snapshots are not counted again. Unavailable usage is `null`; partial usage is explicitly incomplete. Wall time excludes provisioning, independent judging and failure interviews; cache tokens are reported separately, and token totals are not monetary costs. Compare fresh repeated runs, retain failures and provider interruptions, and report this small experiment separately from the complete matrix. Do not change installation or add context-file markers without a measured activation gap and a separately selected paired intervention.

## Judged invariants
- strict focused-spec validation and real evidence execution pass;
- each public workflow turn, each fresh native authoring or publication phase, and BMad regeneration completes a focused-spec loader read, selects an installed CLI with accepted provenance, and obtains valid protocol-1 workflow guidance from that same executable. The first scored execution in a native phase must acquire valid guidance; a late read cannot repair that boundary. Conversational clarification or approval in the same persisted session is not a new workflow boundary and may retain unchanged acquisition. Host-truncated CLI output counts only after a subsequent completed read of that successful command's linked artifact delivers the full valid response. Command starts, failed responses, a different installation, help, or formats/runner guidance alone do not activate the workflow;
- standalone acquisition excludes chained checks such as `test -x … && <CLI> instructions …`; a full artifact read cannot repair a non-standalone invocation. Clipped output without a completed matching artifact read remains unacquired. The package-owned workflow router owns the recovery procedure; neither hidden tool metadata nor an agent's final claim replaces delivered guidance;
  Both the truncation footer's `Read artifact://… for full output` link and the current host's `[raw output: artifact://…]` link identify recoverable stdout. A trailing wall-time annotation is not part of that response. Neither footer is itself acquisition: the paired successful read must still deliver the complete matching package/topic JSON.
- OpenSpec validation and tasks are complete when applicable;
- selected Go and/or pytest evidence actually executes and passes; cases that explicitly require both languages check both;
- existing product tests remain unchanged and pass, except the explicitly editable Python test and implementation in `vacuous-evidence`; its unrelated tests and runner remain protected;
- controlled regressions in every selected implementation make its focused evidence fail;
- judged identity is the `(scope, ID)` pair: selected-scope checks ignore same-ID entries elsewhere, while all-scope checks judge every entry against its own explicit binding and evidence;
- an exact focused ID is required only when the task or pre-existing source supplies it; otherwise one valid authored binding is selected, frozen at the first successful checkpoint, and retained through apply/publication; missing, ambiguous, invalid, or renamed identities fail independently of passing evidence;
- a named change is not an undisclosed scope label: completion selects the one configured scope containing that change's native documents, rejects missing/ambiguous selections, and uses it for CLI, identity and controlled-mutation checks; equivalent exact Go file/package selectors are accepted;
- lifecycle checks independently execute working evidence before publication, stop before the next turn when it fails, and require the same explicit binding and evidence to survive and execute in the configured main scope after working discovery ends; they do not rely on an owner, revision edge, inherited evidence, or an agent's claimed PASS;
- native agent-execution judgment requires a completed successful test command or installed CLI run reporting the exact selected evidence; validation, help, incomplete calls, failed commands and unrelated references do not count;
- the agent does not inspect implementation source or use `shell: true`; public package README/reference documentation and type declarations are permitted, but package `src/`, compiled `dist/` JavaScript, and executable example source are implementation inspection. Invoking the explicit installed `dist/cli.js` with Node is CLI execution, not source inspection. Reading/searching that file or reading it through a shell/inline script still fails integrity, including when combined with a legitimate CLI invocation;
- a Node CLI invocation through a shell-variable project root or within a shell group such as `(cd … && node …/dist/cli.js run)` is still execution, not implementation inspection. Any separate read/search of the same implementation path remains prohibited; this exception does not relax the stricter standalone local-installation matching used for guidance acquisition;
- proposal turns do not start implementation.
- registry placement cases independently load the registry adapter's configured `files`, preserve every original registration at its original domain location, reject an added default monolith, and require either existing-domain reuse or exactly one explicitly connected new-domain source. Configuration outside that format's options remains unchanged; unconfigured evidence and domain-wide reorganization fail.
- specification review/revision cases preserve existing identity and format-owned evidence, reconcile assertions with revised native behavior, and retain unrelated scope-local enrollments. A structurally valid inline/registry representation and old green evidence do not establish semantic correspondence; independent changed-outcome sensitivity remains required. The package-owned workflow owns phase-aware procedure, not this guide.
- upgrade cases retain an independently owned pre-migration inventory and candidate artifact expectation; a green remaining selection cannot hide lost legacy outcomes or package tampering. Supported inline authoring may remain inline under explicit API-2 selection. Non-upgrade cases retain unchanged installed-package/skill protection.

Upgrade preservation compares scope-local identities and ordered evidence with the captured legacy inventory, not hardcoded replacement runner prefixes. Compatible project runners and their IDs may remain; a compatible official-package replacement must preserve selectors, options, timeouts, and execution requirements. Artifact checks require core, the selected format, refreshed integration, and any selected official runners; optional official runners are checked if installed, not required merely because the reference installation contains them.

Revision semantics are read from the actual parser-bound item, including a marked paragraph or list item; a heading is not required. Semantic wording, evidence selection, ownership, and sensitivity remain separate checks: accepting revised prose does not accept retained stale evidence.

Proposal checkpoints compare the starting product tree before apply can run, including newly created executable files. Approval matches complete project-relative paths; prefix and suffix lookalikes do not authorize another file. Sensitivity requires the frozen selected reference to execute and report behavioral `FAIL`, followed by exact restored `PASS`; setup/runner `ERROR`, signals, unrelated failures and failed restoration never count.

Integrity compares final protected-file bytes/hashes with the baseline, not edit history or semantic equivalence. An empty `altered candidate packages=` list means no package-content violation; it does not invalidate authorized dependency installation. Per-reference sensitivity and protected-state preservation remain separate checks.

Direct framework execution proves the exact package/file and selected test actually ran; zero-match Go summaries and wrong-file Python tests are rejected. The same implementation-inspection policy applies to public and native authoring/regeneration transcripts, including directory searches, while public docs/types and CLI execution remain permitted.

Driver exceptions/timeouts record failed turns with bounded available output, and owned process trees terminate before cleanup. Successful transcripts retain their beginning instead of silently tail-truncating. BMad failure interviews resume the last attempted regeneration session. Runtime-loaded eval TypeScript is checked for erasable syntax independently of compiled package source.

The result is written exclusively to gitignored `evals/results/<case>-<timestamp>-<unique-id>.json`; identical timestamps cannot overwrite another run. `--keep-workspace` retains the isolated workspace for diagnosis. A model-specific pass is evidence for that model and prompt; it is not a universal capability claim.

Saved results are immutable. If a gate bug is corrected, captured transcripts may be replayed to verify that correction, but the original model score remains unchanged and the replay is not a new model evaluation. Acquisition recorded at an executed boundary is judged against the serving installation, version, canonical selection, and workflow bytes from that boundary; replay does not reinterpret the historical response against a later final installation state.

Provider HTTP 429 interruptions may be retried with a pause and reduced concurrency. Retain each interrupted invocation and its immutable result, associate every retry with the same case/mode/model and frozen candidate, and report the successful attempt separately from transport history. Retry only observed rate-limit interruptions, not behavioral gate failures; a later success never rewrites an earlier score. A complete retry campaign must still cover every discovered case and native mode.

The tool-free test user handles an explicit disclosure of deferred in-scope work before interpreting completion phrasing or the absence of a question. It requests a concrete remaining proposal or answers a concrete approval request using only the task and conversation; it neither supplies hidden evidence mechanics nor authorizes unproposed files. Explicitly planning-only deliverables and genuinely completed requests still terminate without a follow-up.

For instruction-distribution changes, completion requires fresh runs of every case rediscovered by `--list` and every native host in both revision and `--create` modes. Include newly added inline cases rather than freezing an expected count. Record each model, invocation, immutable result artifact, gate verdict, and exit status; a subset or skipped case is not a complete run. Guidance acquisition is not executable evidence. Historical full-text-skill result files retain their original contract and are never rewritten or relabelled as loader runs.

## Native-ID authoring evaluation

The separate black-box authoring evaluation establishes the production identity/evidence protocol against host-owned checkable items. Editable items may carry a Markdown marker, Gherkin tag, or explicitly selected inline `ID`/`EVIDENCE`; the BMad case binds its generated kernel's stable `CAP-1` through registry `source.path` and `source.nativeId` without modifying derived output. Each agent receives a plain request to create or revise the host specification for blocked-account login, with no focused ID, evidence path, selector, skill-reading instruction, or prohibition on companion files. In revision mode, the existing item rejects blocked accounts without saying what happens when credentials are valid, so the change must sharpen that same item rather than duplicate it.

```sh
node --experimental-strip-types evals/native-pilot.ts openspec externcash/gpt-6-sol
```

Add `--create` to start without the native document and evaluate whether the agent authors the checkable item, identity, and evidence from scratch. The default mode starts with an incomplete native outcome and checks that the same atomic result is revised rather than duplicated. The creation gate checks each host's native item shape and one focused binding; it does not replace unavailable host validators. The BMad case installs its official project skills and scripts, checks memlog use, then removes the derived kernel and invokes `bmad-spec` in a fresh agent turn to rederive it from `.memlog.md`. Its lifecycle verdict requires the same unique `CAP-1` outcome, unchanged registry binding, single behavior source, and protected product/tests after regeneration. The GSD case installs official project-scoped Pi workflow assets under an isolated HOME; their later lifecycle transitions are not exercised.

The BMad generated-kernel fixture pins official skills to commit `48f0ce37e1fc378d6255c90e1b155f2212a6fe33`, immediately before upstream removed `bmad-spec` on 2026-10-12. The official `skills` installer consumes that exact commit's GitHub archive instead of cloning repository history. The official skill bodies remain unchanged. These cases judge that revision's memlog/`CAP-N` contract, not the replacement Product Owner/ticket workflow; a successful historical-host run is not current-BMad certification.

BMad regeneration uses its own fresh persisted session, never the prior authoring context, so clipped guidance can be recovered through that call's output artifacts. Creation identity checks use the CLI parser's actual bound item rather than a hidden scenario/acceptance-heading convention: an OpenSpec requirement heading or Agent OS shaping subsection can own the outcome. The bound item itself must contain the blocked/valid/rejected conditions; an unrelated marked section, detached or duplicate marker, and malformed native syntax still fail.
Focused IDs retain the selected parser's opaque identity contract; no separate lowercase or dotted-ID grammar is imposed by the judge. Non-BMad native items may also use the documented registry `source.path`/`source.nativeId` representation. Authoring and single-source checks use that normalized selection and reject missing, conflicting, detached, or duplicate declarations. BMad retains its generated, unmarked `CAP-1` requirement. Kiro EARS checks examine the selected item after its parsed identity prefix, not a second hidden authoring syntax.
The regeneration memlog gate accepts project-relative or exact in-project absolute paths and read selectors. It requires a paired successful read completion before kernel derivation starts; a failed or unfinished read, a same-named source outside the workspace, or a read after writing the kernel cannot establish canonical derivation.
Negated authentication wording such as “must not log in” or “is not authenticated” expresses rejection; it is not required to use an undisclosed `rejected` token. A statement permitting blocked login still fails the bound-outcome check.
Missing or ambiguous enrollment fails authoring independently of the prose. Without a unique parser-bound item, the bound outcome is **unjudged**, not evidence that native behavior was lost; selection-dependent execution remains unverified. With a unique binding, a wrong outcome is a judged behavioral failure. Correct bound prose alone proves neither evidence execution nor regression sensitivity. Unsupported native validators/lifecycle operations remain separately unverified, never passing authoring by exemption.

Trigger, obligation, attached unique identity, and blocked/valid/rejection semantics remain required. Installed GSD `.pi/gsd-core/` resources and its isolated `.home/.npm/` dependency cache are not native project behavior sources; project duplicates still fail, and installed GSD resources are protected by infrastructure integrity checks.

GSD uses one pinned official Pi installation, not a separate unconverted skill from another runtime. Its installed new-project workflow and requirements template are exposed verbatim as local `gsd-new-project` and `gsd-requirements` skills with discovery frontmatter and source provenance. Preparation rejects stale Claude-home guidance and checks concrete referenced Markdown assets exist. A host read counts only after its matching `read` completion succeeds; line ranges and `raw` selectors are accepted without crediting failed reads or similarly named resources.

## Immutable cross-case reports

The repository-only report reads explicitly selected immutable public/native result artifacts and campaign records; it never scans `evals/results`, replays a gate, launches an agent, or rewrites an input:

```sh
node --experimental-strip-types evals/report.ts \
  --result evals/results/<result>.json \
  --manifest .eval-cache/<campaign>/summary.json

node --experimental-strip-types evals/report.ts \
  --result evals/results/<result>.json \
  --manifest .eval-cache/<campaign>/summary.json \
  --json
```

`--result` and `--manifest` are repeatable, and at least one is required. A manifest has `entries[]`; each entry names `kind` (`public` or `native`), `id`, `mode`, and `attempts[]`. An attempt may record `number`, `resultPath`/`artifact`/`result` or `artifacts[]`, `code`, `signal`, explicit model/candidate metadata, provider statuses/rate-limit state, and provisioning interruption details. Root-relative recorded result paths resolve against the repository root; absolute paths remain absolute. A missing referenced artifact or attempt with no result is retained as a missing-result invocation. An unreadable explicit result/manifest, malformed JSON, unsupported result shape, or malformed manifest/attempt field fails actionably.

JSON schema version 1 includes: `sources` (canonical paths, SHA-256 hashes, roles and references), `duplicates`, `coverage`, every `invocations[]` attempt, unique immutable `results[]`, independent `verdicts`, `interruptions`, `measurements`, guidance denominators/judgments, non-gating acquisition observations in the existing `integrationObservations` field, and `groups.byCaseMode`/`groups.byModelCandidate`. The field name remains unchanged for schema compatibility and accepts both integration-topic and native continuation acquisition observations. Repeated references to one canonical result are identified but counted once; distinct attempts and distinct result files remain separate even when case/mode match. Explicit result identity wins over campaign identity for grouping. Missing model/candidate identity remains `unknown` and receives a result/invocation-specific unknown label rather than being guessed or pooled into a certified comparison. Candidate asset hashes produce a deterministic aggregate candidate identity; booleans such as `candidateAssetsUnchanged` do not.

Public task pass/fail and native `authoring`, `evidence`, `nativeValidation`, and `nativeLifecycle` remain independent. `certified` requires the saved native artifact's certification verdict; exit 2 alone is neither failure nor certification. Failed gates, blocked gates (`passed: null` plus `blockedBy`), unverified native aspects, provider interruption, provisioning interruption and missing results are separate dimensions. A later pass does not erase an earlier failed attempt, and an interruption does not erase a saved behavioral verdict.

Loader reads, workflow acquisition and applicable host-guidance loading report `eligible`, `observed`, `passed`, `failed`, `blocked`, `unobserved`, and `interrupted`. `observed = passed + failed`; the failure rate is `failed / observed`, so zero observed judgments yields `null`/`unavailable`, not a zero-failure claim. Public judgments retain per-turn granularity; native judgments retain their saved combined/phase gate granularity. Explicit provider/provisioning interruptions remain interrupted or unobserved and are never inferred to prove a loader/workflow/host-guidance defect. Historical `EvalResult.observations`, including false `focused-integration-acquired` and native continuation reacquisition observations, remain non-gating and never rewrite task success, certification, exit status, or failure-interview selection.

Measurement totals include only saved public `measurements` or saved native `phaseMeasurements`; historical missing measurements stay missing. Coverage reports measured results, measured usage, complete usage, incomplete usage, and native authoring/lifecycle phases. Valid available fields are summed, while complete-case totals include only `usageComplete` cases. Public duration is scored agent-turn duration. Native duration is the sum of recorded scored native phases. Provisioning, independent judges, test-user responder time and research interviews are excluded; historical campaign wall time is never substituted for missing agent timing.

## Post-failure research interviews

Public and native evaluations use the same read-only post-eval research interview after all scoring and lifecycle checks. If a judged gate fails, the harness resumes that agent's own persisted session before workspace cleanup: the last attempted public workflow turn, or the last attempted native phase (lifecycle when it ran, otherwise authoring). It shows observed gaps and asks for concrete fixes to instructions, fixture, or gates: the exact place and suggested wording or change, the evidence behind each proposal, and how to check the fix. Portable loader and CLI-owned guidance remain framework-agnostic; host-specific paths and commands belong in host guidance or the installation fixture. Keep the agent-facing eval request blind; do not leak skill names, IDs, selectors, or gate expectations into its prompt or judge artifacts.

The result stores a separate `diagnostic` with `status` (`answered` or `unavailable`), `answer`, `transcript`, and `detail`; successful evaluations have `diagnostic: null`. Research has only the `read` tool and a two-minute limit. Its success, failure, or unavailable session never changes the scored turns, gates, verdict, or process exit code. Missing or ambiguous session journals, interview errors, and an absent completed answer are recorded as unavailable rather than discarding the evaluation. The CLI reports diagnostic availability; the complete recommendations are in the saved result. Historical records are not rewritten, and a new interview is not a retry of the scored task.

`diagnostic.answer` retains all completed assistant text responses from the interview in order, not just the last message. A later runtime continuation about unfinished scored-task todos therefore cannot replace earlier recommendations. Machine-readable test-user decisions still use the final assistant response; partial streaming output is not a completed answer.

Interview outcome summaries respect the scored phase: recommendation-only and installation-only cases require no behavioral execution, and an existing-scenario review need not change a correct scenario. Recommendations are research hypotheses, not authoritative gate explanations. Check them against recorded commands and gate details before changing instructions or scoring; replay a suspected gate defect without rewriting the historical result.
