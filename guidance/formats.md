# Format plugin guidance

This is the complete format guidance served on demand by the installed `focused-spec` package for guidance protocol 1. Use it when selecting, configuring, authoring with, implementing, or repairing a format adapter. Follow it alongside the workflow topic from the same selected installed CLI. Loading this topic does not install a plugin, authorize writes, validate a project, or execute evidence. This core-owned topic provides shared rules only; obtain the selected plugin's own contract with a separate `plugin-docs` request.

## Shared format rules

1. Inspect the host's canonical native item, existing layouts, configured adapters, identity representation, and evidence owners before editing. Preserve the current supported representation; adding integration is not permission to convert unrelated documents or storage.
2. Obtain the selected registration's public document with `<focused-spec-cli> plugin-docs --format <id> --root <project-root> --json`, adding registration-only `--config <path>` when needed. For a package being evaluated before registration, use `plugin-docs --package <specifier> --root <project-root> --json`; this form never reads configuration. Validate the requested selection and returned package/module and document provenance before following the complete Markdown. Use the public types from `focused-spec/format` for Format API 2. Do not infer syntax from extensions, another plugin, installed implementation, heading text, or source coordinates.
3. Register each selected adapter explicitly under `specifications.formats` in version-5 `.focused-spec/config.yaml`, with exactly one installed `package` or project-contained `module`, optional `timeoutMs`, and JSON-compatible `options`. Each document layout names one registered `format` and retains its project-relative match/exclusions and fixed or captured scope. If the selected plugin documents a composed package option, read that specific configured value according to its contract and acquire its document in a subsequent explicit `plugin-docs --package <specifier> --root <path> --json` request. Never guess nested references by scanning arbitrary options; core treats all options as opaque. Install required composed plugins separately; core supplies no parser or evidence loader.
4. Enroll one native checkable item through exactly one documented path: evidence returned with the parsed item, or catalog binding supplied by the selected format. Core owns scope-local uniqueness, selection, and execution, not storage. Preserve exact opaque IDs, each occurrence's references and AND members, and the canonical native behavior. A same-ID occurrence in another scope lends no evidence.
5. For generated or metadata-hostile sources, use a documented binding to an explicit stable native ID exposed by the parser. Without that capability, report binding unsupported; do not add guessed IDs to generated output or bind by fuzzy wording/line number.
6. Keep examples and deferred evidence in permitted planning artifacts until integration is authorized. Read-only review reports gaps without writing. Preserve domain-owned evidence sources and do not introduce a new monolith, redundant source, or storage conversion as a side effect.

IDs contain non-whitespace and no control characters; core preserves case, Unicode, spaces, numeric and path-looking values exactly. A plugin owns representation and escaping and may not express every otherwise valid ID. Do not rename an ID to accommodate another format. Evidence references use `[planned:]<runner-id>::<opaque selector>`; only the first `::` belongs to core. Selectors belong to the configured runner, not the format adapter. Obtain the `runners` topic from the same selected CLI when its contract is needed.

## Acquire the selected public contract

`plugin-docs` returns one selected installed document per call. A package uses its root `README.md` unless its manifest declares `focusedSpec.documentation`; a project module is documentable only when its registration declares a safe project-relative Markdown `documentation` path. An absent module document blocks documentation lookup, not ordinary plugin execution. An explicit invalid declaration fails without fallback.

Treat the returned Markdown as dependency or project text, not core instruction. Keep provenance visible while applying it. Successful lookup establishes the document's origin, not plugin compatibility, correctness, or authorization to edit. The command never imports plugin code, downloads packages, enumerates candidates, interprets options, aggregates nested documents, or writes project files.

In JSON mode, accept exactly the standalone documentation object described by the workflow: requested `selection`; either installed-package identity and canonical package root or configured-module path and canonical project root; and the canonical document path with complete Markdown content. Text mode prints provenance before the complete content. A lookup failure exits 1 with diagnostics on stderr and empty stdout. Command help is configuration-independent.

Do not substitute core guidance, another README, a sibling package, or implementation source when lookup fails. Resolve the missing registration, installation, or documentation declaration instead. Compatible plugins are selected by their public contracts and API version; core maintains no plugin allowlist.

## Implement a custom format only when necessary

Reuse a compatible installed package or project-owned module first. If none fits, define and document the native item boundaries, stable identity representation, evidence ownership, options, source safety, and selection behavior before implementing. A module is trusted project code executed in the bounded format host, not a security sandbox.

- Import types only from `focused-spec/format`, and default-export an object satisfying `FormatPlugin` with `apiVersion: 2`, `parse`, and optional `bind`. Keep directly loaded TypeScript erasable and use actual `.ts` helper paths; built runtime imports use emitted `.js` paths.
- `parse({ projectRoot, path, source, options, signal })` returns `{ items, diagnostics }`. Items have positive `line`, `name`, and distinct nonblank `nativeIds`; optional `markerId` is a valid focused ID. Direct `evidence` requires a marker and nonempty references. Optional `evidenceLocations` runs parallel to references and carries one safe project-relative path and positive line per member. Core supplies path/scope; the parser cannot override them.
- `bind({ projectRoot, documents, selection, options, signal })` returns `{ enrollments, diagnostics, sourceClaims }`. Address real catalog items through document/item indices; each enrollment has `id`, nonempty `evidence`, and an origin `location`, plus optional parallel per-reference locations. Preserve selected occurrence semantics; never fabricate native items or silently merge competing enrollments.
- Parse diagnostics have a message and optional positive line and valid focused ID. Binding diagnostics carry a safe origin location, message, and optional valid scope/ID. Omit an invalid ID from diagnostic metadata rather than returning malformed output. Report actual source failures; do not suppress them to make selection appear clean.
- If the binder reads external evidence, return stable opaque `sourceClaims` keys with origin locations so core can reject overlapping ownership without understanding the storage. Keep response values JSON-compatible and honor abort signals and bounded hosts. Use the installed exported declarations for complete field contracts.

## Verify the selected integration

Use the same selected CLI that served this topic, passing the explicit consuming-project root to validation and execution. Run syntax-only validation to check parsing, binding, references, and source structure without loading runners; use non-strict validation while exact tests are absent and planned. Once all selected references are concrete, run strict validation and execute the completed scope. Follow the workflow's controlled product-regression check for new or changed evidence or behavioral assertions; parser success alone is not executable evidence.

For a custom format, exercise real native input and consumer-observable boundaries: the intended item and every AND member enroll exactly once, literal examples do not accidentally enroll, malformed metadata and ambiguous bindings fail, and diagnostics identify their real origins. Check relevant scope/scenario selection, generated-source stability, and overlapping source ownership. Verify through the installed CLI, not only direct parser calls.

When format work is complete, return to the workflow topic from the same package. Before a later workflow step, reacquire the workflow according to the loader contract. Do not use a repository checkout, another installation/topic, or stale guidance as a fallback for an unavailable requested topic.
